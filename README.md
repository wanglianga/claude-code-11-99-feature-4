# 避难所入住与返所 · 柜台排班与开台工作台

供**接待员、楼层值班员、床位管理员、排班协调员、志愿者**共同操作的工作台，包含两大模块（页面顶部切换）：

- **床位与家庭**：让暂时外出的家庭仍有床可回，同时继续接待新到家庭——分房、现场入住、暂离、返所、核实退住各有明确结果，而不是只维护一个全所剩余人数。
- **柜台排班与开台**：接待柜台A 与物资柜台B 都要一名**有相应技能且实际签到在岗**的人才能放号；名义排班不算在岗，一人不能同时支撑两个柜台，交接未确认前暂停放号，已有预约转等待/改约。

纯浏览器前端：React + TypeScript + IndexedDB + WebWorker，计算与持久化全部在本地完成，不依赖后端，不使用真实居民资料（内置虚构家庭、房间与志愿者）。

## 柜台排班与开台：领域规则实现要点

- **名义排班 ≠ 实际在岗**：`planned` 班次只代表计划覆盖；只有**签到**生成的出勤才计入“实际覆盖”，未签到不能开放预约名额。
- **按实际时间区间检验覆盖**：每个柜台在任一时刻都要有一名技能有效、实际在岗者；覆盖用区间求并与缺口计算，**不是把每人总工时相加**（两名志愿者合计工时够、但时段有洞仍判缺岗）。
- **一人不能同时支撑两个柜台**：同一时刻只能有一个柜台的在岗出勤；排班/签到/交接生效时都会重核。
- **两种排班策略**（生成班表时可对比）：
  - **固定跨技能守台**：跨技能人员全程固定守 A/B，短时志愿者在其休息/临时任务时替休（交接少、居民容易找到固定人员）；
  - **短时主班 + 跨技能机动**：按可用时段切段，单技能短时志愿者进主班，跨技能人员补位并保留机动（补临时缺岗快，但接班确认更多）。
- **休息/临时任务与技能资格撤销按区间扣除**：区间内不计计划覆盖、不能签到支撑柜台；**撤销不删除**既有班次与出勤，已发生的服务不回撤；恢复仅对恢复时刻之后生效。
- **签到 / 接班 / 离岗**：签到生成出勤；**迟到签到**自签到时刻起才有实际覆盖，班次开始至签到记为缺口；**离岗回执晚到**按实际离岗时间修订缺岗区间，不撤回已发生的服务。
- **交接（直接替补 / 联动换岗）**：交接需双方确认后生效，**生效前该柜台暂停放号**；已有预约转为「等待」而非继续显示可办理；联动换岗从另一柜台调人并指定补位者，避免原柜台空岗；**双方同时点击只形成一份生效交接**。
- **班表调整不抹去实际出勤**：取消/重排计划班次不影响已落库的出勤区间。
- **跨日班次**：全部时间使用绝对毫秒时间戳，跨日窗口（如 22:00–次日 02:00）无需特殊分支。
- **页面分区展示**：柜台页分别显示**计划覆盖 / 实际覆盖 / 受影响预约 / 待确认接班**。
- 多标签并发、命令幂等、单记录事务与前文床位模块完全一致。

- **家庭不可拆分**：整组家庭只进一个房间；房间容量、共房同意、无障碍要求同时满足才可分配。
- **草稿不占床**：分房草稿不产生床位占用；**现场入住确认后**才计入实际在场人数（确认经由本地模拟适配器异步完成，确认中床位单独预占、不计在场）。
- **暂离 ≠ 退住**：暂离后实际在场人数减少，但住宿关系未结束，返所承诺继续占床（保护中），绝不因人数减少把床让给别人。
- **两条床位保护路径**（都必须兑现返所权）：
  - **原房原床保留**：回程明确，但保护床位期间不参与分配（可能空置紧缺房间）；
  - **容量保护（返所换房）**：家庭须事先同意换房；释放原房，在另一房间保护同等床位作为返所安排，可腾出稀缺房型；返所时回执提示**须向家庭说明新房**。
- **每次变更重核全部承诺**：新分房、返所、延期、关房等都在事务内重新核验房间资格与所有有效返所承诺能否按家庭整组兑现；失效草稿保留输入并说明冲突。
- **到期未归只产生联系核实任务**，不自动认定退住；**退住须楼层值班员核实**（异步确认），核实后结束返所权、释放床位。
- **已入住家庭不得被自动搬走**：关房时如房内仍有在场家庭或「原房原床」承诺则拒绝；「容量保护」承诺可整组迁移到他房，无法迁移则拒绝关闭。
- **多标签并发**：同一站点（origin）多标签共享 IndexedDB；所有写命令在单个 IndexedDB readwrite 事务内「读取→校验→写回」，跨标签天然串行，后到命令在事务重核中得到明确冲突结果。
- **幂等**：每条命令携带 commandId，重复提交只生效一次并开具「重复回执」。

## 本地启动

要求 Node 18+（推荐 22）。

```bash
npm install        # 安装依赖
npm run dev        # 开发模式：http://localhost:5173
```

其他命令：

```bash
npm run test       # 运行领域引擎单元测试（vitest）
npm run build      # TypeScript 检查 + 生产构建到 dist/
npm run preview    # 预览生产构建：http://localhost:4173
```

```bash
docker compose up --build
```

## 演示账号（角色）

无需账号密码。页面右上角下拉切换演示角色，权限由引擎在事务内再次校验：

| 角色 | 权限 |
| --- | --- |
| 接待员 | 登记家庭、草稿分房、提交入住确认、暂离登记、确认返所；柜台放号/改约/取消预约 |
| 楼层值班员 | 核实退住、承诺延期、联系任务备注；办理预约 |
| 床位管理员 | 临时关闭 / 重新开放房间 |
| 排班协调员 | 登记志愿者与可用时间、核准/撤销技能、登记休息与临时任务、生成/手工班表、发起交接、柜台放号、签到（代） |
| 志愿者 | 为本人签到/离岗、确认与本人相关交接、办理预约 |

任何角色都可推进演示时间、查看核对面板与回执流。“志愿者”角色时右上角另选“本人”对应哪位志愿者，签到/离岗只能作用于本人。

## 演示脚本（对应题目要求的验证场景）

### A. 床位与家庭（切到「床位与家庭」标签）

初始场景即题目示例：A 房 6 床（无障碍）、B 房 6 床（普通）；王芳与女儿 2 人在住 B；李强一家 4 人在住 A（不需无障碍、已同意返所换房）；赵敏一家 3 人（需无障碍）待安置。演示时间 15:00。

1. **两条保护路径对比**
   - 李强一家「暂离登记」选**原房原床保留**（至 18:00）→ A 房在场 0、保护中 4、可分配 2；赵敏一家仍无法安置，待安置面板给出原因（A 可分配 2<3；B 无无障碍）。
   - 右上角「重置演示数据」后改选**容量保护 → 保护于 B 房** → A 释放 6 床，B 在场 2+保护 4；赵敏一家可草稿分房到 A 并入住。
2. **四人家庭按时返所**：李强一家「确认返所」→ 容量保护路径下安排到 B 房，回执注明「返所换房说明：原 A 房 → 现 B 房，请向返所家庭说明新房」；原房保留路径则回到 A 房原床。
3. **重复暂离回执**：暂离成功后，该家庭行出现「模拟重复提交暂离回执」按钮（以相同 commandId 重发）→ 回执流出现「重复提交已幂等忽略」，承诺仍只有一条。
4. **保护房间临时关闭**（床位管理员）：B 房有在场家庭时关闭被拒；王芳退住后关闭 B，可把李强的容量保护整组迁移到 A；若 A 剩余不足 4 床则拒绝关闭并说明「无法整组兑现」。
5. **两标签同时分房**：开两个浏览器标签（同一地址）。李强暂离（容量保护）且赵敏入住 A 后，A 仅剩 3 床：标签 1 为吴磊一家（3 人）创建草稿并提交入住确认；标签 2 为另一家庭创建草稿——草稿失效并显示冲突原因，输入保留可重试。
6. **中途刷新**：任何操作中途刷新页面，状态从 IndexedDB 恢复，未完成的异步确认由 worker 启动时补结算。
7. **承诺到期未归**：暂离至 18:00 后用「+1小时」推过 18:00 → 自动生成联系核实任务（不自动退住、床位继续保护）。
8. **全所核对**：右侧「全所核对」实时校验床位与柜台两侧不变量。

### B. 柜台排班与开台（切到「柜台排班与开台」标签）

演示数据：接待柜台A、物资柜台B 在 **14:00–16:00** 连续开放；V1 刘晨仅 A 技能、可用 14:00–15:00；V3 何静仅 B 技能、可用 15:00–16:00；V2 郑凯、V4 孙涛 两岗技能齐全、全程可用。初始班表为**固定守台**（V2 守 A、V4 守 B，均已在 14:00 签到），演示时间 14:00。预置预约：A 14:10–14:30、B 14:40–15:00、B 15:10–15:30。

1. **两种班表都有效、后者各时段另有机动**
   - 初始页面可见「固定守台」：V2 守 A、V4 守 B，计划与实际覆盖均连续。
   - 结束两条在岗（签到/离岗面板对 V2、V4 离岗）后，在「班表」里按 14:00–16:00 点「生成：短时主班+机动」→ 前段 V1 守 A / V2 守 B，后段 V4 守 A / V3 守 B；覆盖面板“机动”一栏前半段显示 V4、后半段显示 V2。分别签到后两段实际覆盖都连续。
2. **名义排班不等于开台**：只生成班表、不签到，到「预约」为该柜台放号 → 预约直接进入「等待」，提示“时段无实际在岗者覆盖”；「柜台覆盖」实际覆盖条显示缺口。
3. **14:30 B 负责人临时离岗**：在「签到/接班/离岗」对 V4 点「离岗（现在）」（或补录 14:30 离岗回执）→ B 立刻「暂停放号」，B 的预约（14:40、15:10）转为「等待」，办理按钮消失。
   - **直接替补**：在「交接」选 B、接班人 V2，发起 → 显示待确认接班、暂停放号；V2 若仍在 A，需先离岗或改用联动；确认后 B 恢复，预约自动复原。
   - **联动换岗**：发起时勾选“联动换岗”并指定补位人（如 V1 补 A）→ 双方确认后 V2 调守 B、V1 接 A，两柜台同时有人。
4. **交接双方同时点击只生效一份**：对同一待确认交接重复点确认 → 第二次提示“已生效”，生效交接只有一份，出勤只有一条。
5. **班表调整不抹去实际出勤**：取消某条计划班次 → 历史出勤仍在、覆盖不回退；离岗回执晚到（补录 14:30 离岗但 14:55 才提交）→ 按实际离岗 14:30 修订缺岗区间，14:00–14:30 服务保留。
6. **跨日班次**：在「班表」把窗口设为 22:00–02:00（结束早于开始视为跨日），点「+ 柜台A / + 柜台B」新增跨日开放窗口，登记两名 22:00–次日 02:00 可用的跨技能志愿者后生成班表 → 计划覆盖与签到覆盖都按绝对时间区间连续。
7. **休息 / 临时任务重叠**：在「志愿者与资质」给 V2 登记 14:45–15:15 休息 → 覆盖面板计划与实际都在该区间出现缺口，14:50 时 A 暂停放号，15:20 恢复。
8. **技能资格被撤销**：对 V4 撤销 B 技能 → B 自撤销时刻起计划/实际都出现缺口、预约转等待；恢复技能后覆盖复原（此前缺口不回填）。
9. **迟到签到**：清除 V2 的签到，14:40 再签到 → 出勤标“迟到签到”，14:00–14:40 记为实际缺口，受影响预约转等待。
10. **页面分别显示**：柜台覆盖面板并列 **计划覆盖 / 实际覆盖 / 受影响预约 / 待确认接班**；全所核对含“一人不同时支撑两个柜台 / 计划覆盖按区间检验 / 实际覆盖（当前时刻）/ 交接唯一生效”。

```
  test/
    engine.test.ts    # 床位领域引擎测试
    roster.test.ts    # 柜台排班与开台引擎测试
    ui-smoke.test.tsx # 柜台面板 SSR 渲染测试
```

关键设计：

- **单记录事务状态**：整份状态存于 IndexedDB 单条记录，命令在事务内完成「读→引擎校验→写回」，多标签并发由 IndexedDB 序列化，杜绝脏写。
- **完全一致的覆盖口径**：`engine.ts` 与 `roster.ts` 的覆盖/缺口/冲突计算是纯函数，页面展示与命令校验共用同一实现，避免“显示能开、实际不能办”。
- **区间而非总量**：覆盖以合并后的时间区间与缺口判断；总工时只作为排班提示，绝不用于证明任一时刻有人。
- **异步确认（本地模拟适配器）**：入住确认、退住核实先落库为待结算单（带应结算真实时间戳），worker 定时清扫结算；刷新后任一标签的 worker 启动即补结算。
- **虚拟时钟**：业务时间（承诺到期、签到/离岗、覆盖）使用可推进的演示时钟；异步确认的模拟网络时延使用真实时钟，两者互不干扰。
- **数据安全**：全部数据仅存于本浏览器 IndexedDB，清除站点数据即可彻底删除；无任何网络请求与后端依赖。
